# Автодеплой Фоточки: GitHub Actions → VPS

Каждый `git push` в ветку `main` сам проверяет и выкладывает сайт на сервер. Руками на сервер заходить не нужно.

```
git push ──► GitHub Actions ──► автотесты ──► архив кода по SSH ──► VPS
                                  │ упали                              │
                                  ▼                                    ▼
                         выкладки нет, сайт        новая версия → /api/health
                         не тронут                     ок → готово
                                                       не ок → автоматический откат
```

**Почему так, а не Coolify.** Сервер маленький (1 ядро, 1 ГБ), а Coolify нужно минимум 2 ядра и 2 ГБ. Здесь на сервере ничего лишнего: Node.js, nginx и два небольших скрипта.

## Что в комплекте

| Файл | Где живёт | Что делает |
|---|---|---|
| `.github/workflows/deploy.yml` | в репозитории | Тесты и отправка кода на сервер |
| `deploy/server/setup-autodeploy.sh` | запускается один раз на сервере | Настраивает пользователя, ключ, права |
| `deploy/server/fotochka-deploy` | `/usr/local/bin` на сервере | Принимает код, ставит зависимости, перезапускает, проверяет, откатывает |
| `deploy/server/fotochka-deploy-wrap` | `/usr/local/bin` на сервере | Пропускает от GitHub только SHA коммита, остальное отклоняет |

**Как защищено**
- У GitHub свой ключ, и он умеет ровно одно — запустить выкладку. Shell, туннели и любые другие команды запрещены.
- Пользователь `deploy` без пароля; через sudo ему доступен только скрипт выкладки.
- Сервер сверяется по отпечатку (`DEPLOY_KNOWN_HOSTS`), подменить его незаметно нельзя.
- На сервер уходит только код из git. `.env` и `data/` (настройки и заказы) выкладка не трогает. Если `.env` случайно попал в репозиторий, выкладка останавливается.
- Зависимости ставятся от пользователя `fotochka`, не от root.

## Разовая настройка (~30 минут)

Исходное состояние: сайт уже работает на сервере по `DEPLOY.md` (папка `/opt/fotochka`, служба `fotochka`).

### 1. Репозиторий на GitHub

В папке проекта на компьютере проверь `.gitignore`. В нём должны быть строки:

```
.env
data/
node_modules/
```

Скопируй в проект папки `.github` и `deploy/server` из комплекта. Затем создай на GitHub **приватный** репозиторий `fotochka` (пустой, без README) и отправь в него код:

```
git init
git add .
git status
```

В выводе `git status` не должно быть `.env` и `data/`, только `.env.example`. Если они там есть, сначала поправь `.gitignore`.

```
git commit -m "Фоточка + автодеплой"
git branch -M main
git remote add origin https://github.com/JaneEva08/fotochka.git
git push -u origin main
```

Первый пуш запустит workflow, и он упадёт на шаге выкладки: секретов ещё нет. Это нормально.

### 2. Ключ для GitHub Actions

На компьютере (PowerShell):

```
ssh-keygen -t ed25519 -f "$HOME\.ssh\fotochka_actions" -C "github-actions-fotochka"
```

На вопрос о кодовой фразе дважды нажми Enter. Здесь фраза не нужна: ключ будет храниться в секретах GitHub и умеет только запускать выкладку.

### 3. Настройка сервера

С компьютера отправь на сервер скрипты и публичный ключ (`IP` замени на адрес сервера):

```
scp -r deploy\server root@IP:/root/autodeploy
scp "$HOME\.ssh\fotochka_actions.pub" root@IP:/root/autodeploy/
```

На сервере (`ssh root@IP`):

```
cd /root/autodeploy
bash setup-autodeploy.sh IP "$(cat fotochka_actions.pub)"
```

В конце скрипт напечатает строку вида `IP ssh-ed25519 AAAA...`. Скопируй её, это секрет `DEPLOY_KNOWN_HOSTS`. Сверь отпечаток, который он выводит, с тем, что ssh показывал при твоём первом входе на сервер.

### 4. Секреты в GitHub

Репозиторий → **Settings → Secrets and variables → Actions → New repository secret**:

| Имя | Значение |
|---|---|
| `DEPLOY_HOST` | IP сервера — ровно как в первом слове строки known_hosts |
| `DEPLOY_KNOWN_HOSTS` | строка из шага 3 |
| `DEPLOY_SSH_KEY` | всё содержимое файла `fotochka_actions` (без `.pub`), включая строки `BEGIN` и `END` |

Содержимое приватного ключа можно открыть Блокнотом: `notepad $HOME\.ssh\fotochka_actions`.

После этого приватный ключ на компьютере можно удалить. Он нужен только GitHub, а если понадобится, легко сделать новый.

### 5. Проверка

1. Поменяй заметную мелочь на сайте, например текст в подвале.
2. `git commit -am "Проверка автодеплоя"` → `git push`.
3. GitHub → вкладка **Actions** → запуск **Deploy**. Оба этапа должны стать зелёными, в логе последняя строка `готово: на сайте версия ...`.
4. Открой сайт в режиме инкогнито — правка на месте.
5. Какая версия сейчас на сервере: `cat /opt/fotochka/REVISION`.

## Каждый день

Правишь код → `git push` в `main`. Всё.

- **Тесты упали** — выкладка не начинается, на сайте остаётся прошлая версия.
- **Новая версия не стартовала** — скрипт сам вернёт прошлую, а в Actions будет красный крестик с причиной.

## Откат

**Через GitHub (обычный способ).** Actions → **Deploy** → **Run workflow** → в поле `sha` вписать SHA нужного коммита. Его видно в истории коммитов на GitHub.

**Вручную на сервере (если GitHub недоступен).** Последние 5 версий лежат в `/opt/fotochka-releases`, там же `initial` — снимок сайта до автодеплоя.

```
ls -lt /opt/fotochka-releases
V=initial   # или SHA нужной версии
rsync -a --delete --exclude=/.env --exclude=/data/ /opt/fotochka-releases/$V/ /opt/fotochka/
chown -R fotochka:fotochka /opt/fotochka
systemctl restart fotochka && curl -s http://127.0.0.1:3047/api/health
echo $V > /opt/fotochka-releases/CURRENT
```

## Восстановление на новом сервере

Код хранится в GitHub. С сервера заранее нужно сохранить только две вещи:
- **`.env`** — пароли и ключи. Держи копию в менеджере паролей.
- **`data/`** — заказы. Копию делай регулярно: `scp -r root@IP:/opt/fotochka/data ./backup-data`.

Порядок на чистом Ubuntu:
1. `DEPLOY.md` шаги 1–2: DNS на новый IP, Node.js 22, nginx, certbot.
2. Пользователь и папки:
   ```
   useradd --system --home /opt/fotochka --shell /usr/sbin/nologin fotochka
   mkdir -p /opt/fotochka/data
   ```
   Положи `.env` (права `chmod 600`) и восстанови `data/` из копии.
3. Служба: скопируй `deploy/fotochka.service` из репозитория в `/etc/systemd/system/`, затем `systemctl daemon-reload && systemctl enable fotochka`.
4. Шаг 3 этой инструкции (`setup-autodeploy.sh`).
5. Обнови секреты `DEPLOY_HOST` и `DEPLOY_KNOWN_HOSTS`, затем Actions → Deploy → **Run workflow**.
6. `DEPLOY.md` шаг 6: nginx и HTTPS.

## Если что-то не так

| Сообщение в Actions | Причина и решение |
|---|---|
| `Permission denied (publickey)` | Ключ в `DEPLOY_SSH_KEY` не пара тому, что ставили в шаге 3, или скопирован не целиком. Ещё вариант — в настройках SSH на сервере есть `AllowUsers` без `deploy` (скрипт настройки об этом предупреждает). |
| `Host key verification failed` | `DEPLOY_HOST` не совпадает с первым словом в `DEPLOY_KNOWN_HOSTS`, или сервер переустановлен — заново возьми строку из шага 3. |
| `Connection timed out` | Неверный IP, сервер выключен или SSH на нестандартном порту. Ещё вариант — файрвол хостера или `ufw` пускает на порт 22 только российские адреса, а серверы GitHub за рубежом. Проверь правила в панели хостера. |
| Падает этап «Автотесты» | Тесты не прошли — это и есть защита. Если тестам нужен браузер (Playwright), его нужно ставить в workflow отдельным шагом. |
| `npm не смог поставить зависимости` | Сервер не достучался до npm или не хватило памяти. Сайт при этом не менялся. |
| `не запустилась, сайт возвращён на ...` | Ошибка в новой версии. Подробности: `journalctl -u fotochka -n 50 --no-pager`. |

## Данные и 152-ФЗ

Сервер находится в России: заказы (`data/`) и настройки (`.env`) хранятся только на нём.

Через GitHub (США) проходит только код. Персональных данных в нём нет: `.env` и `data/` в git не попадают, а если `.env` всё же попал, скрипт выкладки остановится. Логи GitHub Actions содержат только сообщения выкладки, без заказов.

Бэкапы `data/` храни на своём компьютере или на другом сервере в РФ, не в зарубежных облаках.
